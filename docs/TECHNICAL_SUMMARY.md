# Atlas AI Summit Agents: Technical Summary

Oct 14, 2026 · @Nicolette

## Overview

Both parts are built, deployed and measured against a fictional conference, the Atlas AI Summit (18 to 19 November 2026). Part 1 answers 30/30 development questions correctly at about half a US cent each. Part 2 catches 8 of 8 deliberately planted data errors on live Gmail and Google Calendar data.

The two parts share one dataset: Part 1's speaker directory is Part 2's reference data.

## Part 1: RAG over structured documents

Every question is routed to the path that can answer it correctly, rather than sent to one retriever.

**Knowledge base (three structured formats).** `sessions.csv` (40 sessions), `speakers.json` (25 speakers) and `venue_guide.pdf` (tabular PDF: rooms, ticket tiers, policies). The data is generated by a seeded script, so it is reproducible byte for byte and frozen with a SHA-256 manifest (KB v1.0.3). Traps are planted deliberately: a cancelled session, a moved session, a room that is not wheelchair accessible, a co-presented session, and two speakers named Jon and John Mokoena.

**Ingestion and chunking.** One chunk per record, not fixed-size text splits. Each row is written as a self-describing sentence and denormalised at index time, so a session chunk also names its room and speakers. PDF tables are extracted with pdfplumber, one chunk per row plus a summary chunk per table. Emails and phone numbers are kept out of chunk text (data minimisation). 82 chunks in total.

**Query routing (query transformation).**

1. **ID lookup.** A question containing an ID (`S-010`, `SP-008`, `R-04`) is resolved by exact lookup and pinned to the top, with no LLM call to route it.
2. **SQL.** Counts, averages and "most/least" questions go to text-to-SQL over DuckDB. A view, `sessions_active`, encodes the rule that cancelled sessions are excluded from counts.
3. **Retrieve.** Hybrid BM25 + vector search (local `bge-small` embeddings), fused with weighted reciprocal rank fusion.
4. **Rewrite + retrieve.** Questions with no shared keywords are rewritten by Claude Haiku into conference-programme vocabulary, three ways, then retrieved and fused.

Retrieved session chunks are expanded through their foreign keys, so the linked room and speakers come along automatically. Claude Sonnet writes the final answer from numbered, delimited context blocks and must cite them. Code then removes any citation that was not actually in the context, and "not in the knowledge base" is a structured flag, not a phrase.

**Traceability in the UI.** Each answer shows its route, citations (expandable to the source chunk), the generated SQL and result rows, the rewrites used, latency and cost.

## Part 1: key decisions, each backed by a measurement

I measured retrieval before adding an LLM, so every component had to earn its place on the 19 retrievable gold questions (full table in `evals/ABLATION.md`).

| Decision | Evidence | Outcome |
| --- | --- | --- |
| Route by question type instead of one retriever | Vector search alone: 3/5 semantic but 3/6 ID lookups; hybrid: 6/6 lookups but 0/5 semantic at rank 1 | Neither wins everywhere, so the router picks per question |
| Pin IDs by exact lookup | Rank fusion pushed a dominant BM25 hit to rank 2 | Lookups 6/6 at rank 1, lower latency |
| Expand context through foreign keys | Cross-document completeness rose from 1/4 to 4/4 | Kept: zero added latency |
| Cross-encoder reranker | Improved cross-document but lowered overall rank-1 recall (13 to 11) and added about 290 ms | Measured and rejected |
| LLM query rewrite for keyword-free questions | Semantic questions went from 1/5 (retrieval only) to 5/5 end to end | Kept on that route only |
| SQL for aggregation | Counting questions cannot be answered from five retrieved chunks | 7/7 aggregation correct |
| Brute-force numpy vector search, no vector database | 82 chunks; exact search beats approximate search at this size | Swap to pgvector or LanceDB past about 100k chunks |

**Safety of text-to-SQL.** A plain `SELECT` in DuckDB can read local files and URLs through functions such as `read_csv`. So the generated SQL is parsed with sqlglot (single SELECT only, allow-listed tables, no file-reading functions), external access is disabled and locked at the engine level, and results are capped at 100 rows with a 5-second timeout. A test proves file reads fail even if the parser check were bypassed.

## Part 1: results

The system answers 30/30 development questions correctly, refuses all 4 unanswerable ones, and costs about US$0.005 per answer.

| Question type | Correct |
| --- | --- |
| ID lookup | 6/6 |
| Aggregation (SQL) | 7/7 |
| Semantic (no shared keywords) | 5/5 |
| Cross-document | 4/4 |
| Policy (from the PDF) | 4/4 |
| Unanswerable (must refuse) | 4/4 |

Route accuracy was 29/30, false refusals 0, and citation validity 26/26. Latency is 3.7 s median and 6.4 s at p95; a full 30-question run costs US$0.16.

**How the score got there.** The first end-to-end run scored 25/30. Of the 5 failures, 1 was a real bug (SQL output truncated by a token limit, fixed with a retry path), 3 were bugs in my own scorer, and 1 was a test item that contradicted a design decision: it expected an email address, which is deliberately excluded from retrievable text. It was replaced, and the change is recorded in the changelog.

**Honest caveat.** 30/30 is on the development set the system was tuned against, so it is optimistic. A sealed held-out set of 15 unseen questions exists to give the unbiased number; it is guarded in code so it can only run once, at submission.

**Held-out result, run once at submission: 14/15.**

| Question type | Correct |
| --- | --- |
| ID lookup | 3/3 |
| Aggregation (SQL) | 3/3 |
| Semantic (no shared keywords) | 1/2 |
| Cross-document | 3/3 |
| Policy (from the PDF) | 2/2 |
| Unanswerable (must refuse) | 2/2 |

Route accuracy was 15/15 and citation validity 12/12. The one miss, H-012, was a semantic question: the system answered "not in the knowledge base" instead of finding S-008. That is a false refusal, not a wrong or fabricated answer. It withheld rather than guessed, so the failure mode failed safe. Full result in `evals/baselines/e2e_heldout_final.json`.

## Part 2: agent with tools, extraction and verification

The agent turns 9 messy RSVP emails and 2 calendar events into a verified list of 8 unique attendees, with every correction and flag recorded per field.

**Tools (three, plus the LLM).** Gmail (reads RSVPs sent to a dedicated `+atlas` address), Google Calendar (events titled "Atlas AI Summit"), and web access (an HTTP fetch of the published speaker directory). Claude Haiku is called through the Anthropic API for extraction.

**Flow.**

1. **Extract.** The LLM reads each email body and returns `{name, organisation, email, phone}` as JSON, with null for anything not stated. The Gmail From header is never passed to it, because every test email was sent from one account; identity must come from the body.
2. **Validate and self-correct.** Code checks each extraction (valid JSON, name present, email format). A failure is sent back to the LLM once with the exact validation error. If it still fails, the item is flagged `extraction_failed` instead of guessed. Every retry is recorded.
3. **Parse the calendar.** Attendee lines in event descriptions are parsed by code, with no LLM.
4. **Normalise.** Names trimmed, emails lowercased, South African phone numbers normalised for comparison.
5. **Verify against the directory.** Each person is matched on email, phone, and fuzzy name and organisation similarity. Typos are corrected to the directory value only when the identity match is strong, and the original value is kept in `changes`. A missing email is filled from the directory when name and phone agree.
6. **Flag what should not be guessed.** If the best name match and the best organisation match point to different people, the row is flagged ambiguous and left for a human. An email that differs from the directory is flagged, not overwritten silently. Nobody matched becomes a new delegate.
7. **Deduplicate** across all emails and events by speaker ID, otherwise by email or phone.
8. **Output.** One row per attendee with status, sources, changes and flags, exported as CSV; a final node scores the run against an answer key.

The design rule throughout: **the LLM extracts, deterministic code verifies.** Correction, matching and deduplication are rules that can be tested, not model judgement.

## Part 2: results

On live Gmail and Calendar data, the agent caught **8 of 8 planted errors** and produced exactly the 8 expected attendees.

| Planted error | Expected behaviour | Result |
| --- | --- | --- |
| Messy phone format | Match on digits | Passed |
| Misspelled organisation | Correct to directory spelling | Passed |
| Missing email | Fill from directory (name + phone agree) | Passed |
| Same person RSVPs twice, name typo | Merge into one attendee | Passed |
| Jon vs John Mokoena with the other's organisation | Flag ambiguous, do not guess | Passed |
| Email differs from directory | Flag the mismatch | Passed |
| Person not in the directory | Add as new delegate | Passed |
| Organisation typo in a calendar event | Correct via directory and email | Passed |

The errors were planted in synthetic seed data with a written answer key (`data/synthetic/part2_answer_key.json`), so the score is checked, not claimed. The same logic also passes 8/8 offline in `n8n/test_logic.mjs`.

**Debugging that shaped the design.** The first live run flagged every email as `extraction_failed` rather than inventing data. The cause was Gmail returning base64-encoded message bodies, so the LLM received empty text; nine calls with identical 223-token inputs gave it away. A second issue was the directory download arriving as raw text instead of JSON. Both were fixed, and the failure itself showed the verification layer doing its job: no fabricated attendees.

## Tools and data sources

| Layer | Choice | Why |
| --- | --- | --- |
| Part 1 language and UI | Python, Streamlit Community Cloud | Custom retrieval and evaluation; free public hosting |
| Embeddings | fastembed `BAAI/bge-small-en-v1.5` (local, ONNX) | No API cost per query, no PyTorch, fits free-tier memory |
| Keyword search | rank-bm25 | Exact IDs and names |
| Structured queries | DuckDB + sqlglot guard | Aggregations; parse-and-lock defence |
| LLMs | Claude Haiku 5.5 (routing, rewrite, Part 2 extraction), Claude Sonnet 5.5 (answers) | Cheap model where it suffices, stronger model for the final answer |
| Part 2 orchestration | n8n Cloud | Managed Google connectors, visual reasoning chain |
| Part 2 tools | Gmail, Google Calendar, HTTP (published directory) | The three required tool types |
| Engineering | uv, pytest (135 tests, network blocked in tests), ruff, gitleaks pre-commit | Reproducible, safe-by-default development |

All people, organisations and events are fictional. Every email address uses the reserved `example.com` / `example.org` domains, so nothing can reach a real inbox.

## Limitations and what I would improve with more time

**Known limitations**

- Evaluation is a single run on small sets (30 development, 15 held-out). The models used do not expose a temperature setting, so answers can vary slightly between runs.
- The rewrite route takes about 9 seconds because it makes extra LLM calls; answers are not streamed.
- Free hosting sleeps when idle, so the first load after a quiet period can take 30 to 60 seconds.
- Part 2: phone numbers are normalised for matching but not always rewritten in the output rows, and the change log sometimes records "email filled from directory" when an email was already present.
- Part 2 runs on demand from the n8n canvas, not on a schedule or trigger.
- The session question counter in the UI is off by one.

**With more time**

- Stream answers and run the rewrite calls in parallel to cut rewrite-route latency.
- Repeat evaluations several times and report variance; grow both test sets.
- Host Part 1 on Azure Container Apps with a minimum of one replica to remove cold starts.
- Add tracing (Langfuse) for per-request visibility in production.
- Part 2: trigger on new emails, add a human review queue for flagged rows, and write verified rows to a sheet or CRM.
- Replace fuzzy matching thresholds with a small labelled set, so match confidence is calibrated rather than hand-tuned.

## How it was built

I built this with AI-assisted development (Claude Code) over about 15 hours across two days, with the design decisions, review and debugging driven by me. The brief suggested 2.5 to 3 hours. I went beyond that deliberately and spent the extra time on evaluation, safety and debugging rather than features, because those are what make an agent trustworthy in production.
